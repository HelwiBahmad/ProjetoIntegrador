3. ARQUITETURA DO SISTEMA

PADRÃO DE ARQUITETURA: MVC (Model-View-Controller) + Service Layer + Repository

```
┌─────────────────────────────────────────────────────────────┐
│                    HTTP CLIENT (Browser)                     │
│              HTML5 + CSS3 + JavaScript Vanilla               │
│                  Requisições JSON (GET/POST/PUT/DELETE)     │
│                        ↓        ↑                            │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│                     EXPRESS.JS SERVER                        │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ ROUTES LAYER                                           │  │
│  │ Define endpoints (/api/noticias, /api/eventos, etc)  │  │
│  │ Middleware (autenticação, CORS, etc)                  │  │
│  └────────────────────┬─────────────────────────────────┘  │
│                       │                                      │
│  ┌────────────────────▼─────────────────────────────────┐  │
│  │ CONTROLLERS LAYER                                    │  │
│  │ Recebem requisição HTTP (req, res)                  │  │
│  │ Delegam ao Service                                   │  │
│  │ Retornam resposta JSON padronizada                  │  │
│  │ No projeto: NoticiaController, CategoriaController │  │
│  └────────────────────┬─────────────────────────────────┘  │
│                       │                                      │
│  ┌────────────────────▼─────────────────────────────────┐  │
│  │ SERVICES LAYER                                       │  │
│  │ Lógica de negócio (sem req/res)                     │  │
│  │ Validações de regras                                │  │
│  │ Chamadas ao Repository                              │  │
│  │ Tratamento de erros                                 │  │
│  └────────────────────┬─────────────────────────────────┘  │
│                       │                                      │
│  ┌────────────────────▼─────────────────────────────────┐  │
│  │ REPOSITORIES LAYER                                   │  │
│  │ Abstração do acesso a dados                          │  │
│  │ Queries SQL parametrizadas                           │  │
│  │ Relacionamentos (FK, joins)                          │  │
│  │ Proteção contra SQL Injection                        │  │
│  └────────────────────┬─────────────────────────────────┘  │
│                       │                                      │
│  ┌────────────────────▼─────────────────────────────────┐  │
│  │ UTILS LAYER                                          │  │
│  │ ApiResponse Factory (padronizar respostas)          │  │
│  │ Helpers e utilitários                                │  │
│  └────────────────────┬─────────────────────────────────┘  │
│                       │                                      │
└───────────────────────┼──────────────────────────────────────┘
                        │
                        ▼
        ┌───────────────────────────────┐
        │   DATABASE (SQLite)           │
        │   arquivo: banco.db (local)   │
        └───────────────────────────────┘
```

FLUXO DE UMA REQUISIÇÃO TÍPICA:

1. Cliente → GET /api/noticias?categoria=1&pagina=1

2. Routes Layer
   ↓ router.get('/refactor', NoticiaController.listar)

3. Controller Layer
   ↓ static listar(req, res) {
       const filtros = req.query
       const resultado = NoticiaService.buscarTodas(filtros)
       return res.json(ApiResponse.success(resultado))
     }

4. Service Layer
   ↓ static buscarTodas(filtros) {
       const noticias = NoticiaRepository.buscarTodas(filtros)
       const total = NoticiaRepository.contar()
       return { noticias, total, paginacao }
     }

5. Repository Layer
   ↓ static buscarTodas(filtros) {
       let query = 'SELECT * FROM Noticia WHERE publicado = 1'
       if (filtros.categoria) query += ' AND categoriaId = ?'
       return db.prepare(query).all(...params)
     }

6. Database executa query

7. Resposta retorna para o cliente (JSON padronizado)

6.2 ESTRUTURA DE TABELAS
------------------------

6 Tabelas Principais com Relacionamentos:

USUARIO (Tabela base de autenticação):
  Colunas: id, nome, email(UNIQUE), senha(hash), tipo, avatar, bio, dataCriacao, ativo
  Índices: email
  Relacionamentos: 1 → N Noticia, 1 → N Historia

NOTICIA (Conteúdo principal):
  Colunas: id, titulo, slug(UNIQUE), resumo, conteudo, imagem, categoriaId(FK), 
           autorId(FK), destaque, publicado, dataCriacao, dataAtualizacao
  Índices: slug, categoriaId, publicado, autorId
  Relacionamentos: N ← 1 Usuario, N ← 1 Categoria

CATEGORIA (Organização):
  Colunas: id, nome, slug(UNIQUE), descricao, icone, cor, ativo
  Índices: slug, ativo
  Relacionamentos: 1 → N Noticia

EVENTO (Calendário):
  Colunas: id, titulo, descricao, data, local, acessibilidade, ativo, dataCriacao
  Índices: data, ativo
  Relacionamentos: Nenhum (tabela independente)

HISTORIA (User-generated content):
  Colunas: id, titulo, conteudo, usuarioId(FK), nomeAutor, emailAutor, cidade, estado,
           aprovado, publicado, dataCriacao
  Índices: usuarioId, aprovado, publicado
  Relacionamentos: N ← 1 Usuario

DIREITO (Informações legais):
  Colunas: id, titulo, descricao, numeroLei, linkOficial, categoria, ativo, dataCriacao
  Índices: ativo, categoria
  Relacionamentos: Nenhum (tabela independente)

6.3 TRANSAÇÕES ACID
-------------------

SQLite suporta:
  ✓ Atomicidade: Operação completa ou nenhuma
  ✓ Consistência: Dados sempre válidos
  ✓ Isolamento: Leituras não interferem
  ✓ Durabilidade: Dados persistem em arquivo

Exemplo:
  db.exec('BEGIN TRANSACTION');
  try {
    db.prepare('INSERT INTO...').run();
    db.prepare('UPDATE...').run();
    db.exec('COMMIT');
  } catch (erro) {
    db.exec('ROLLBACK');
    throw erro;
  }

6.4 ÍNDICES PARA PERFORMANCE
-----------------------------

Índices criados no inicializarBanco.js:
  ├─ Usuario: idx_email (UNIQUE)
  ├─ Noticia: idx_slug, idx_categoria, idx_publicado
  ├─ Categoria: idx_slug
  ├─ Historia: idx_usuario, idx_aprovado
  └─ Direito: idx_categoria

Benefícios:
  ✓ Busca por email: O(log n) em vez de O(n)
  ✓ Filtros por categoria: O(log n)
  ✓ Queries parametrizadas protegidas

6.1 REPOSITORY PATTERN
----------------------

Categoria: Padrão Estrutural
Problema: Isolar lógica de dados da lógica de negócio
Solução: Abstração do acesso a dados através de Repository

Benefício Principal: Se mudar de SQLite para PostgreSQL, só muda o Repository.
Services não conhecem SQLite, fácil testar, trocar banco sem quebrar código.

Implementação:
  Arquivos:
    - servidor/repositories/NoticiaRepository.js
    - servidor/repositories/CategoriaRepository.js
    - servidor/repositories/EventoRepository.js
    - servidor/repositories/HistoriaRepository.js
    - servidor/repositories/DireitoRepository.js

Exemplo NoticiaRepository:
  class NoticiaRepository {
    static buscarTodas(filtros = {}) {
      let query = 'SELECT * FROM Noticia WHERE publicado = 1';
      let params = [];
      
      if (filtros.categoria) {
        query += ' AND categoriaId = ?';
        params.push(filtros.categoria);
      }
      
      return db.prepare(query).all(...params);  // Parametrizado = seguro
    }
    
    static criar(dados) {
      const stmt = db.prepare(`
        INSERT INTO Noticia (titulo, conteudo, categoriaId, autorId)
        VALUES (?, ?, ?, ?)
      `);
      return stmt.run(...Object.values(dados));
    }
  }

Vantagem de Abstração:
  Código antigo (depende do SQLite):
    class NoticiaRepository {
      static criar(dados) {
        db.query('INSERT INTO...') // SQLite direto
      }
    }
  
  Se mudar para MongoDB = quebra tudo
  
  Novo código (abstrato):
    class NoticiaRepository {
      static criar(dados) {
        return this.persistir(dados)  // Método abstrato
      }
    }
  
  Se mudar para MongoDB = só muda a implementação de persistir()

6.2 SERVICE LAYER PATTERN
-------------------------

Categoria: Padrão Arquitetural
Problema: Lógica de negócio misturada com HTTP request/response é difícil testar
Solução: Camada Service separada que não conhece HTTP

Benefício Principal: Lógica pura, testável, reutilizável em CLI, WebSocket, gRPC

Implementação:
  Arquivos:
    - servidor/services/NoticiaService.js
    - servidor/services/CategoriaService.js
    - servidor/services/EventoService.js
    - servidor/services/HistoriaService.js
    - servidor/services/DireitoService.js

Exemplo NoticiaService:
  class NoticiaService {
    // NEM RECEBE req/res - só dados puros
    static criar(dados, usuarioId) {
      // VALIDAÇÕES
      if (!dados.titulo || dados.titulo.trim() === '') {
        throw new Error('Título é obrigatório');  // Erro puro
      }
      
      if (dados.titulo.trim().length < 5) {
        throw new Error('Título deve ter pelo menos 5 caracteres');
      }
      
      // LÓGICA DE NEGÓCIO
      const existente = NoticiaRepository.buscarPorSlug(dados.slug);
      if (existente) {
        throw new Error('Slug já existe');  // Regra de negócio
      }
      
      // CHAMADA REPOSITORY
      const noticia = NoticiaRepository.criar({
        ...dados,
        autorId: usuarioId
      });
      
      return noticia;  // Retorna dado puro
    }
  }

Como Controller usa Service:
  class NoticiaController {
    static criar(req, res) {
      try {
        // Validação HTTP (autenticação)
        if (!req.usuario) {
          return res.status(401).json(ApiResponse.unauthorized());
        }
        
        // Chama Service (lógica pura)
        const noticia = NoticiaService.criar(req.body, req.usuario.id);
        
        // Formata resposta HTTP
        return res.status(201).json(
          ApiResponse.success(noticia, 'Notícia criada', 201)
        );
      } catch (erro) {
        // Converte erro puro em resposta HTTP
        return res.status(400).json(
          ApiResponse.error(erro.message, 400)
        );
      }
    }
  }

6.5 MIDDLEWARE PATTERN
----------------------

Categoria: Padrão de Estrutura
Problema: Lógica transversal (autenticação, CORS, etc)
Solução: Middleware que intercepta requisições

Implementação:
  Arquivo: servidor/rotas/rotasAutenticacao.js
  
  function verificarToken(req, res, next) {
    const token = req.headers.authorization?.split(' ')[1];
    
    if (!token) {
      return res.status(401).json(ApiResponse.unauthorized());
    }
    
    try {
      const decoded = jwt.verify(token, process.env.JWT_SECRET);
      req.usuario = decoded;
      next();  // Passa para próximo middleware/controller
    } catch (erro) {
      return res.status(401).json(ApiResponse.unauthorized());
    }
  }

Uso:
  router.post('/noticia', verificarToken, NoticiaController.criar);
  // verificarToken executa ANTES de NoticiaController.criar

7. PRINCÍPIOS SOLID
================================================================================

7.1 S - SINGLE RESPONSIBILITY PRINCIPLE (SRP)
----------------------------------------------

Definição: Cada classe deve ter uma única razão para mudar (uma responsabilidade)

MAU EXEMPLO (Violando SRP):
  class Noticia {
    validar() { /* validação */ }        // Responsabilidade 1
    salvar() { /* persistência */ }      // Responsabilidade 2
    toJSON() { /* formatação */ }        // Responsabilidade 3
    formatarEmail() { /* email */ }      // Responsabilidade 4
  }
  // Problema: Mudar layout do email, banco, validação ou formato = muda a classe

BOM EXEMPLO (Respeitando SRP):
  class Noticia {
    constructor() { /* apenas dados */ }
  }
  
  class NoticiaService {
    static criar(dados) { /* apenas lógica de negócio e validação */ }
  }
  
  class NoticiaRepository {
    static criar(dados) { /* apenas persistência */ }
  }
  
  class NoticiaController {
    static criar(req, res) { /* apenas HTTP */ }
  }

Benefício em Nosso Projeto:
  Se mudar validação → Muda só NoticiaService
  Se mudar banco     → Muda só NoticiaRepository
  Se mudar HTTP      → Muda só NoticiaController
  Cada mudança = segura, isolada

7.2 O - OPEN/CLOSED PRINCIPLE (OCP)
------------------------------------

Definição: Aberto para extensão, fechado para modificação
Adicionar funcionalidade sem alterar código existente

MAU EXEMPLO (Violando OCP):
  class NoticiaService {
    static criar(dados) {
      if (!dados.titulo) throw new Error('Título obrigatório');
      if (dados.titulo.length < 5) throw new Error('Mínimo 5');
      if (!dados.conteudo) throw new Error('Conteúdo obrigatório');
      
      // Adicionar nova validação = muda a função existing
    }
  }

BOM EXEMPLO (Respeitando OCP):
  class Validador {
    static validacoes = [
      { campo: 'titulo', regras: ['required', 'minLength:5'] },
      { campo: 'conteudo', regras: ['required', 'minLength:20'] }
    ];
    
    static validar(dados) {
      for (const validacao of this.validacoes) {
        this.aplicarRegras(dados[validacao.campo], validacao.regras);
      }
    }
  }
  
  // Adicionar novo validador = não muda código existing
  // classe Validador está fechada para modificação, aberta para extensão

7.3 L - LISKOV SUBSTITUTION PRINCIPLE (LSP)
--------------------------------------------

Definição: Objetos de uma classe derivada devem poder substituir objetos da classe base

MAU EXEMPLO (Violando LSP):
  class Repository {
    buscar(id) { /* implementação */ }
  }
  
  class RepositorioErrado extends Repository {
    buscar(id) {
      throw new Error('Não implementado');  // Quebra o contrato!
    }
  }

BOM EXEMPLO (Respeitando LSP):
  class Repository {
    buscar(id) { /* implementação */ }
  }
  
  class SQLiteRepository extends Repository {
    buscar(id) {
      return db.prepare('SELECT * FROM ...').get(id);
    }
  }
  
  class MongoRepository extends Repository {
    buscar(id) {
      return db.collection.findOne({ _id: id });
    }
  }
  
  // Ambas implementam o contrato completamente
  // Podem ser usadas intercambiavelmente

7.4 I - INTERFACE SEGREGATION PRINCIPLE (ISP)
----------------------------------------------

Definição: Clients não devem depender de interfaces que não usam

MAU EXEMPLO (Violando ISP):
  interface Repositorio {
    buscar();
    criar();
    atualizar();
    deletar();
    exportarCSV();
    importarXML();
    gerarRelatorio();
  }
  
  class RepositorioSimples implements Repositorio {
    // Precisa implementar TODOS, mesmo que não precise de exportarCSV
  }

BOM EXEMPLO (Respeitando ISP):
  interface Crud {
    buscar();
    criar();
    atualizar();
    deletar();
  }
  
  interface Exportador {
    exportarCSV();
    importarXML();
  }
  
  class RepositorioSimples implements Crud {
    // Só implementa o que precisa
  }
  
  class RepositorioAvancado implements Crud, Exportador {
    // Implementa tudo
  }

7.5 D - DEPENDENCY INVERSION PRINCIPLE (DIP)
----------------------------------------------

Definição: Depender de abstrações, não de concretizações

MAU EXEMPLO (Violando DIP):
  class NoticiaService {
    constructor() {
      this.repo = new SQLiteRepository();  // Depende de concretização
    }
  }
  
  // Problema: Se mudar para PostgreSQL, precisa mudar NoticiaService

BOM EXEMPLO (Respeitando DIP):
  class NoticiaService {
    constructor(repository) {
      this.repo = repository;  // Depende de abstração
    }
  }
  
  // Uso:
  const repo = new SQLiteRepository();
  const service = new NoticiaService(repo);
  
  // Mudar para PostgreSQL = só cria outro Repository, NoticiaService fica igual

PASSO 1: REGISTRAR NOVO USUÁRIO

  ↓
PASSO 2: VERIFICAÇÃO NO BACKEND

  ↓
PASSO 3: HASH DA SENHA
  bcryptjs.hash(senha, 10)
  ↓
PASSO 4: SALVAR NO BANCO
  INSERT INTO Usuario (nome, email, senha_hash, tipo)
  ↓
PASSO 5: RETORNAR SUCESSO
  { id, nome, email, tipo }

---

PASSO 1: LOGIN
  POST /api/autenticacao/login
  { email, senha }
  ↓
PASSO 2: BUSCAR USUÁRIO
  SELECT * FROM Usuario WHERE email = ?
  ↓
PASSO 3: VERIFICAÇÃO
  Usuario existe? (404 se não)
  Senha corresponde? (bcrypt.compare)
  ↓
PASSO 4: GERAR TOKEN JWT
  payload = { id, tipo }
  token = jwt.sign(payload, JWT_SECRET, { expiresIn: '7d' })
  ↓
PASSO 5: RETORNAR TOKEN
  { token, usuario: { id, nome, tipo } }
  ↓
PASSO 6: CLIENTE ARMAZENA TOKEN
  localStorage.setItem('token', token)

---

PASSO 1: USAR TOKEN EM REQUISIÇÕES
  Authorization: Bearer <token>
  GET /api/noticias
  ↓
PASSO 2: MIDDLEWARE VERIFICA TOKEN
  token = req.headers.authorization.split(' ')[1]
  decoded = jwt.verify(token, JWT_SECRET)
  req.usuario = decoded
  ↓
PASSO 3: CONTROLLER ACESSA USUÁRIO
  req.usuario.id
  req.usuario.tipo
  ↓
PASSO 4: LÓGICA CONTINUA COM PERMISSÕES
  if (req.usuario.tipo === 'admin') { /* ... */ }

---

PASSO 1: TOKEN EXPIRA APÓS 7 DIAS
  jwt.sign({...}, JWT_SECRET, { expiresIn: '7d' })
  ↓
PASSO 2: CLIENTE TENTA USAR TOKEN EXPIRADO
  Authorization: Bearer <token_expirado>
  ↓
PASSO 3: SERVIDOR REJEITA
  jwt.verify() lança erro "Token expirado"
  ↓
PASSO 4: RETORNA 401
  { status: 'unauthorized', message: 'Token inválido ou expirado' }
  ↓
PASSO 5: CLIENTE REDIRECIONA PARA LOGIN
  localStorage.removeItem('token')
  window.location.href = '/login'

10. GUIA DE DESENVOLVIMENTO
================================================================================

10.1 CONFIGURAÇÃO INICIAL
--------------------------

1. CLONAR REPOSITÓRIO
   git clone <repo-url>
   cd Projeto-Libras

2. INSTALAR DEPENDÊNCIAS
   npm install

3. INICIALIZAR BANCO DE DADOS
   npm run init-db
   Isso cria o arquivo banco.db com tabelas

4. INICIAR SERVIDOR
   npm run dev
   Ou: npm start
   Servidor roda em http://localhost:3000

5. ABRIR NO NAVEGADOR
   http://localhost:3000

10.2 STACK TECNOLÓGICO
-----------------------

Frontend: HTML5 + CSS3 + JavaScript ES6+
Backend: Node.js + Express.js
Banco: SQLite + better-sqlite3
Autenticação: JWT + bcrypt
HTTP: Fetch API + CORS
Upload: Multer

10.3 PADRÕES DE CÓDIGO
-----------------------

CRIAR NOVA ENTIDADE (ex: Comentario)

1. Model (database schema)
   - Definir no inicializarBanco.js
   - CREATE TABLE Comentario (...)

2. Repository
   - servidor/repositories/ComentarioRepository.js
   - Métodos: buscarTodas(), buscarPorId(), criar(), atualizar(), deletar()

3. Service
   - servidor/services/ComentarioService.js
   - Lógica de negócio: validações, regras
   - Métodos: buscarTodas(), criar(), atualizar(), deletar()

4. Controller
   - servidor/controllers/ComentarioController.js
   - Métodos: listar(), buscarPorId(), criar(), atualizar(), deletar()
   - Manejo HTTP: req, res, status codes

5. Routes
   - servidor/rotas/rotasComentariosRefator.js
   - Definir endpoints (GET, POST, PUT, DELETE)
   - Middleware de autenticação

6. Frontend
   - public/js/comentarios.js
   - Fetch API para chamar endpoints
   - Atualizar UI

10.4 DESENVOLVENDO UMA FEATURE
-------------------------------

Exemplo: Adicionar campo "imagem" em Histórias

PASSO 1: Banco de Dados
  - Adicionar coluna: ALTER TABLE Historia ADD COLUMN imagem TEXT;
  - Ou atualizar initializeDb.js se é novo

PASSO 2: Repository
  - HistoriaRepository: update método para incluir imagem
  
PASSO 3: Service
  - HistoriaService: validar imagem (URL válida?)
  
PASSO 4: Controller
  - HistoriaController: enviar imagem na resposta
  
PASSO 5: Routes
  - Já definidas, apenas retornarão novo campo
  
PASSO 6: Frontend
  - public/js/app.js: renderizar imagem em história

PASSO 7: Testar
  - POST /api/historias/refactor com imagem
  - Verificar em GET se campo volta

10.5 COMANDOS ÚTEIS
--------------------

Iniciar servidor em desenvolvimento:
  npm run dev

Reinicializar banco de dados:
  npm run init-db

Ver erros no código:
  - Abrir DevTools do navegador (F12)
  - Abrir VS Code problems (Ctrl+Shift+M)

Reset completo:
  1. Deletar banco.db
  2. npm run init-db
  3. npm run dev
